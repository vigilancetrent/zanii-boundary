# Zanii Boundary: distributed Linux profile v2

This is a separately versioned deployment contract. The v1 no-network profile remains supported. Static validation, local SQL fixtures and TCP relay tests do not establish Linux containment, provider IAM, live recovery or deployment readiness. No eligible host has been supplied; live acceptance is BLOCKED.

The topology uses a networkless agent with a read-only Unix socket mount. A small relay forwards opaque bytes to the fixed gateway service. The gateway authenticates the original client certificate end to end. Relay connection failures never cause reconnect or replay. Gateway/resource replicas share PostgreSQL authority; each realm has independent data/audit keys and separate app, worker, archive, backup, rotator and migrator credentials. Archive/backup processes have no application decryption keys. Rotator/migrator services run only under the maintenance Compose profile.

The current topology provides same-host application replica redundancy. It has no independently measured failure domains and makes no multi-AZ or whole-cluster disaster recovery claim. Logical backups are limited to one tenant and 64 MiB, restored into a fresh quarantined realm with fresh grants required. Remote PostgreSQL throughput at that limit is unvalidated. Backup services receive 2 GiB, require at least `12 * snapshot bytes + 64 MiB` available, and have a 31-second database acquisition/query budget inside a 240-second job budget. Read-only MVCC snapshots bind tenant RLS without taking the business mutation lock. The live gate tests an independent write while a snapshot remains open.

## Prepare an eligible host

Use Linux with rootful Docker and daemon `userns-remap`. This nftables variant rejects rootless engines and remote Docker endpoints. Use independently verified product and monitoring image digests; the deliberately invalid placeholders cannot produce acceptance. Dedicated internal ingress/runtime networks separate each Compose project. The provider network is a local user-defined bridge with exactly the profile's one IPv4 subnet, default IPAM and explicit driver options `com.docker.network.bridge.gateway_mode_ipv4=nat`, `com.docker.network.bridge.enable_ip_masquerade=true`, `com.docker.network.bridge.enable_icc=false`. Every attached role's actual IPv4 source must lie in that range. macvlan/ipvlan/overlay, extra subnets, direct-routing modes and IPv6 allocations/routes are rejected; monitoring is a separately managed internal network. Agents join neither. IPv6 is unsupported by this profile and the live gate rejects it.

Prepare actual copies of every `config/*.json.example`, the profile, Compose file and acceptance examples outside this checkout. Replace provider DNS/IPs, TLS trust and all key IDs and audience/issuer settings with actual infrastructure values. Every declared provider address/port must be reviewed; metadata and general internet targets remain denied. Supply the public-only trust directory, per-role files and agent credentials. The provider firewall is a host-admin prerequisite: `node scripts/distributed-acceptance.mjs --print-egress-rules` prints the dedicated nft JSON for review, never applies it. The gate compares the actual table exactly and performs egress denial probes. A host without verified firewall authority remains BLOCKED.

Do not assign host bind ownership using raw container IDs. First start a disposable container using the verified image and the same daemon mapping, without secrets or network. Inspect its host PID with Docker, then read `/proc/<pid>/uid_map` and `gid_map`. Each line is `container_start host_start length`; the host ID is `host_start + container_id - container_start`. The exported `mappedContainerId` helper rejects unmapped or identity mappings. Provision every role's host directory/file using those measured mappings, and verify ownership/readability from inside each actual role container before activation. Daemon mapping changes require reprovisioning and fresh acceptance.

Secret source files must be regular, non-symlink, mode `0400`, owned by the mapped role UID. Compose file-backed secrets can retain host ownership; do not depend on Compose uid/gid/mode overrides. Where realms share key bytes, provision distinct role-owned copies instead of weakening owner-only reads. Agent identity directory is mode `0500`, its private key/token mode `0400`, all mapped to agent UID 10003. The socket directory is mode `0750`, mapped relay UID 10004 and group 2000; the relay creates a `0660` socket. Agent receives that directory read-only. Backup spool directories are `0700` and owned by the mapped backup UID. Config files and public trust must be readable inside their intended roles. Shared trust accepts only these public files: `ca.pem`, `postgres-ca.pem`, `provider-ca.pem`, `monitoring-ca.pem`, `issuer.jwks.json`, `broker.jwks.json`, `distributed-evaluator.pem`, and `{archive,backup}-{gateway,resource}-public.pem`. It parses CA certificate chains, public Ed25519 SPKI keys and strictly public Ed25519 JWKS serialized with compact `JSON.stringify` or its two-space format (duplicate JSON keys are rejected); unknown or opaque files and private JWK fields are rejected. Private credentials belong only in their role-specific secret mount. Every role's `/tmp` is an exact bounded noexec/nosuid tmpfs owned by its container UID/group2000, mode1770; the live gate performs a tiny write/stat/remove inside each actual role.

Log directories are mapped role UID and mapped group 3000, mode `02750`; files are `0640`. The monitoring collector UID 20001/group 3000 receives selected role directories read-only. There is no Docker socket or broad host log mount. Provision a real filesystem quota and free-space alarms: `logQuotaBytes` is a planning/readiness floor, not a host quota installer. Bound stale replica stream retention operationally. Default max-pool planning consumes 94 runtime connections plus 4 administration and 3 PostgreSQL reserved connections: 101 of 128. It includes both realms, maximum app/worker replicas and manual rotator/migrator sessions. Backups also reserve their 2-GiB memory limits in host capacity planning.

## Verify and activate

Run `node scripts/distributed-acceptance.mjs --static` to validate checked-in contracts. For actual files, call `readDistributedDeploymentFiles(deploymentDirectory,{configurationDirectory,composeFile})` and set both application `deployment.profileDigest` fields to its calculated digest; the digest excludes only those two self-references. Set exact digest-pinned `deployment.imageRef`. New configuration/image/authority changes require a new evaluation. No script invents image digests or containment authority.

The separate `node --test test/acceptance-distributed-relay.mjs` gate exercises actual Linux Unix sockets and SIGKILL stale-socket recovery; it fails explicitly on Windows and does not establish Docker containment.

The live evaluator needs an explicit acceptance configuration, a dedicated certificate-bound operator identity in an `acceptance-*` tenant with `runtime:admin runtime:read`, independent TLS database inspection credentials, native nft inspection permission, and actual running services. It creates only synthetic tasks for a nonexistent document and does not dispatch business actions. Use narrow, separately issued platform-tenant probe tokens for the probe configurations; these contain `runtime:health runtime:metrics`, never invoke/admin scopes.

`node scripts/distributed-acceptance.mjs --config /secure/acceptance.json --execute` performs real engine/image/userns, mount/ownership, network/firewall, relay, cross-replica authority, independent PostgreSQL sessions, maintenance heartbeat and concurrent snapshot/write observations. It exits 2 with a BLOCKED result for missing prerequisites or failed observations. Only a successful evaluator can emit a new v2 receipt via explicit `--signing-key /secure/evaluator.pem --out /secure/new-receipt.json`. This does not auto-sign other images or configurations. Receipts expire within 15 minutes and cannot be substituted for v1 receipts.

Run explicit prepared exercises using `node scripts/failover-acceptance.mjs --config /secure/failover.json --execute`, or the equivalent `scaling-acceptance.mjs` and `rollout-acceptance.mjs`. Failover kills one actual app replica, observes bounded ready recovery and restores its container. Scaling requires measured sustained saturation with no database pool wait, respects profile replica/pool limits, makes an actual same-image scale event and restores the original count after cooldown. Neither asserts representative-load capacity. A durable mode-0700 controller directory contains exclusive per-project lock files. Crashes, ambiguous Docker outcomes or failed reconciliation retain the lock: inspect and restore actual state before an operator removes that specific file. There is no automatic takeover or business-operation retry.

Rollout requires separately prepared images/projects/ingress networks/socket directories with independent valid v2 receipts, shared authority and combined surge headroom. The default 128-slot PostgreSQL budget is insufficient for two full 101-slot plans and correctly blocks that exercise. A verified candidate alone does not establish a route switch. Without a prepared routing controller, the result is BLOCKED. An explicit controller uses pinned mTLS and Ed25519 signed responses at only `GET /v1/runtime/route/status` and `POST /v1/runtime/route/apply`. Signed state is `{version:1,purpose:'runtime-route-state',nonce,generation,stableOrigin,target:{profileDigest,imageRef,runtimeDigest},changeId,observedAt,expiresAt}`. Apply takes `{version:1,expectedGeneration,target,changeId,nonce}` and atomically increments generation. Nonces and a maximum 30-second signed lifetime are checked. Rollback occurs only while the observed generation, exact target and unique change ID remain owned by this exercise; a foreign change is never overwritten. Acceptance samples the actual stable ready endpoint across candidate switch and rollback. It reports controlled readiness traffic, not a production traffic or failure-domain claim.

Keep source-instance fencing, provider credential revocation, recovery-point age, deletion reconciliation and fresh mission authorization in the independent restore activation process. Neither Compose replicas nor a fresh verification of an old snapshot repair recovery-point loss.

Docker's documented firewall coverage applies to bridge networks and excludes macvlan/ipvlan/host drivers; this profile deliberately supports the narrow local NAT bridge variant. See [packet filtering](https://docs.docker.com/engine/network/packet-filtering-firewalls/) and [bridge options](https://docs.docker.com/engine/network/drivers/bridge/).
