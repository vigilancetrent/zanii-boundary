# Asynchronous domain and ownership contract

The product domain now uses an asynchronous storage port. Policy, memory, learning, document, execution, audit evidence, coverage and A2A methods that read or change persistence return promises. Callers must await them, including readiness, recovery, protocol notifications and ledger status. Pure action/metadata validation, hashing, profiles, baseline detection, `policy.authorityDigest()` and offline signature verification remain synchronous.

`openConfiguredStore({config, material})` selects SQLite or PostgreSQL from validated storage configuration. `asAsyncStore(store)` adapts the legacy synchronous SQLite port once per store object; a shared queue and transaction owner prevent unrelated calls from interleaving with an awaited transaction. The old synchronous `openStore()` contract remains available for legacy callers. Database transactions use `transaction(async () => ..., {tenantId})`; provider HTTP calls, signing services and classification hooks run outside those transactions. See [storage and recovery](product-architecture.md#storage-and-recovery) for the storage boundary and [operations](product-operations.md) for deployment and recovery prerequisites.

Each executable operation claims a durable `operation:<id>` lease before reservation. Admission, dispatch and terminal transitions carry the live owner and fence. Startup recovery respects another replica's live lease. Once ownership expires, recovery records uncertainty; reconciliation claims a new observation lease and reads the independent provider outcome. Reconciliation never repeats a business operation. The resource receives signed owner, fence and expiry claims, checks the signed deadline again after awaited metadata, and runs its entire transaction within that deadline. Its own idempotency journal prevents duplicate effects. Gateway and resource stores have distinct realms and credentials; a resource cannot query the gateway's private lease table.

Cached and reconciled private results finish classification and quarantine before their final policy snapshot. Provider metadata is fetched outside the final database transaction; that transaction records read taint and rechecks current task lineage and permissions. A final identity/task/request clock check follows commit before returning a payload. Revocation serializes with this last authority snapshot; it does not retract a release or external effect already admitted. The HTTP server also checks identity and request expiry immediately before protected responses.

MCP sessions supplied with a store persist tenant, actor, protocol version, initialization and expiry. Session initialization quota changes are atomic across replicas; a session never grants task authority. The standalone adapter's optional no-store mode remains process-local. Authenticated identity rate counters likewise use an atomic tenant transaction. Peer admission and connection concurrency remain local to each server process. Local maintenance enumerates the durable tenant inventory; PostgreSQL application roles delegate inventory maintenance to a separately authorized worker.

Zanii foreground receipt writers acquire a durable DID lease. Exact receipt bytes must enter the encrypted outbox under that lease before SDK network submission. The final SDK fetch rechecks ownership and durable receipt authorization. A new public SDK instance loads the current chain head for each leased record; stale or unsaved in-memory queues are discarded rather than uploaded. Remote signers and uploads inherit the request/lease deadline. Recovery only submits saved exact receipts and does not authorize business replay. `ledger.status()` reads durable pending inventory, so another writer's pending work is visible after restart.

`integrations.zanii.required` defaults to `true`: configured receipts gate actions and blocked recovery prevents readiness. With explicit `false`, the integration supports optional proof/recovery operations; it is detached from the action executor and credential broker. Responses report `requiredForActions:false`, `receiptPolicy:"local-journal-only"` and a degraded feature when pending proof recovery blocks the optional integration. That mode retains the core durable operation journal and independent resource authorization, and makes no external receipt-before-effect claim. Status marked `not-probed` does not establish upstream availability. Malformed configuration or unsafe secret files still fail startup. The resource integration is mandatory for actions and rejects `required:false`.

The local regression suite exercises owner expiry, duplicate admission, fresh-fence reconciliation, two DID writers, stale/hanging signatures, delayed grant reads, late content release, learning deletion races, cross-replica sessions and quotas. PGlite tests execute PostgreSQL SQL locally; they do not establish TCP failover, replication, distributed capacity or deployed Linux containment. Historical milestone evidence remains unchanged in `archive/milestone-2/`. Production acceptance still requires real infrastructure and external service identities.
