# Zanii Boundary capacity measurement contract

`config/capacity.example.json` declares **5 requests/second as a planning assumption**, not a customer target. The planning run schedules60 seconds at10 requests/second, a120-second soak at10 requests/second, then15-second cohorts at20,40 and80 requests/second until the first failing saturation cohort. Each cohort has its own fixture and5-second warmup. The workload is100% authorized synthetic document reads through `POST /v1/actions`, using32 seeded documents of1024 bytes. This does not represent customer traffic, approved peak demand or a production hardware ceiling.

The driver uses monotonic scheduled arrivals independent of request completion. It counts every planned arrival as issued, dropped for scheduling lag, dropped at its in-flight ceiling, or aborted after an authority/configuration error. It never queues missed arrivals invisibly or retries an operation. Request latency starts when a request is issued; scheduled end-to-end latency and scheduling lag have separate distributions and sample counts. Every issued outcome has an HTTP status or explicit transport/unresolved state. Warmup events are retained and excluded from measured throughput.

Each action has a new operation ID across the whole run. Tasks have separate roots with at most1000 authorized actions each; the harness creates enough roots for the planned cohort and never raises production policy limits. Token/task lifetime and result retention extend beyond the cohort, drain and setup margin. It stops on401/403, invalid tasks/quotas, stale authority and deadline mistakes, reporting an invalid run rather than a capacity ceiling. Warmup failures return an `INVALID` report with exact status/code, arrival accounting, observed effects and local ledger/Runtime counters instead of masking the reason. A bounded drain failure remains unverified; it never claims complete effect reconciliation while requests remain outstanding.

The effect oracle reads the resource's durable records independently of gateway responses. Every observed effect must match an issued operation's actor, action and exact document. Dropped arrivals cannot have effects; duplicate/wrong-document effects and successful responses without effects invalidate the run. Effects without a successful response are counted explicitly and never retried. Per-endpoint p50/p95/p99 targets, configured gateway/resource admission limits and the driver's own in-flight/lag limits are recorded separately from the first measured constraint. A driver limit, an admission limit, or an unreached ceiling never becomes a hardware-breaking-point claim.

`core-only` measures the existing gateway/resource boundary with SQLite and real loopback mTLS. `runtime-preflight-local-ledger` additionally exercises the actual pinned Runtime0.4.0 authorization preflight, the retained SDK0.5.4 broker path, nested SDK0.6.0 and a local mTLS signed receipt service. Its report includes actual before/after counters and deltas for Runtime calls/authorization and accepted intent/result receipts. A configuration flag alone cannot establish that profile was exercised. The Runtime preflight authorizes an exact read; it grants no additional company authority and dispatches no separate business tool. The local ledger establishes no live company integration claim.

CPU, RSS, heap and event-loop samples belong to the combined driver, gateway, resource and optional local ledger process. Database byte samples include each SQLite database and sidecars. Startup/seeding and oracle work are outside measured request throughput; the resource sampler itself is inside the measured scope. Independent service CPU, deployed PostgreSQL pool pressure and production disk/cluster capacity remain unknown. Application JSON byte totals exclude headers, TLS, retransmissions and provider network/billing egress. They are not a billed-egress estimate or a byte-month storage quantity.

Run a prepared configuration with `node scripts/capacity-acceptance.mjs --config config/capacity.example.json --out /secure/new-capacity-report.json`. The output is exclusive-create and includes the before/after implementation digest. Source changes invalidate the run. A full planning run must wait for the final Phase4 source/dependency freeze; current unit and short TLS smoke checks generate no canonical measurement artifacts. The `smoke` mode permits short test windows but is always reported as `SMOKE_ONLY` and cannot satisfy the sustained/soak qualification. Final core/full-feature runs must use separate output files and the same declared workload settings for a meaningful comparison.

No eligible Linux staging host or customer workload has been supplied. Distributed containment, provider IAM/Object Lock, independent-session deployed saturation, scale events, recovery under representative traffic, and multi-AZ resilience remain separate blocked acceptance gates. Local measurement never inherits those claims.
